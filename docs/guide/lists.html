Quick start

Lists

A list renders each item of an array signal as a row and keeps the rows it has already built. When the array changes, only new items are rendered, and rows that stay are moved at most.

signal.map

signal.map(render) takes a signal of an array and a function that returns a node for one item. The item itself is the key, so a row is reused when the same item is still in the array. An item replaced by a copy gets a new row.

The result is a live value, so pass it directly as the children of an element. 

import { ul, li } from 'fiorejs';
import { state, flush } from '@fiorejs/signals';

const names = state(['Ada', 'Grace']);

const list = ul(names.map((name) => {
  console.log('render', name);
  return li(name);
}));
document.body.append(list); // logs "render Ada", "render Grace"

names.set([...names.get(), 'Linus']);
flush(); // logs "render Linus" only
console.log(list.children.length); // 3
import { state, flush } from '@fiorejs/signals';

const names = state(['Ada', 'Grace']);

const list = (

      console.log('render', name);

  </ul>

flush(); // logs "render Linus" only

Keyed lists

signal.for().map(render) keys rows by item.key. signal.for((item) => item.id).map(render) keys them by what the function returns. Use it for objects, because a new copy of an object with the same key then keeps its row.

In a keyed list render gets the item as a read-only signal, not as the item. A new array that keeps a key with another object, such as an immutable update of one record, keeps the row and its nodes and sets the item signal, so only the bindings that read it update. Read the current item with todo.get(), and bind a field with todo.computed((item) => item.text). A key that leaves the array and comes back gets a new row. 

import { ul, li } from 'fiorejs';
import { state, flush } from '@fiorejs/signals';

const todos = state([
  { id: 1, text: 'Write docs', done: false },
  { id: 2, text: 'Publish', done: false },
]);

const list = ul(
  todos.for((todo) => todo.id).map((todo, index) => {
    console.log('render', todo.get().text, 'at', index);
    return li.props({ className: todo.computed((item) => (item.done ? 'done' : '')) }).create(todo.computed((item) => item.text));
  }),
);
document.body.append(list);

todos.set(todos.get().map((todo) => (todo.id === 1 ? { ...todo, done: true } : todo)));
flush();                                 // no render: row 1 stays and its class changes
console.log(list.children[0].className); // done
todos.set([{ id: 3, text: 'Release', done: false }, ...todos.get()]);
flush();                                 // logs "render Release at 0"
console.log(list.children.length);       // 3

signal.map(render) without a key still passes the plain item, because it keys by the item itself and the item of a row never changes.

Selecting a row

selector(source) returns a function isSelected(key) that gives a boolean signal, true while source equals key. When source changes, only the readers of the old and the new key run again, so highlighting the selected row costs two updates in a list of 10 or of 10,000 rows. A key is forgotten when nothing reads it. 

import { ul, li } from 'fiorejs';
import { classList, flush, selector, state } from '@fiorejs/signals';

const rows = state([{ id: 1, text: 'Ada' }, { id: 2, text: 'Grace' }, { id: 3, text: 'Linus' }]);
const selected = state(1);
const isSelected = selector(selected);

const list = ul(
  rows.for((row) => row.id).map((row) =>
    li
      .props({ className: classList({ selected: isSelected(row.get().id) }) })
      .on({ click: () => selected.set(row.get().id) })
      .create(row.computed((item) => item.text)),
  ),
);
document.body.append(list);

list.children[2].click();
flush();
console.log([...list.children].map((li) => li.className)); // [ '', '', 'selected' ]

console.log([...list.children].map((li) => li.className)); // [ '', '', 'selected' ]

How rows are kept and moved

When the order changes, only the rows that are out of place are moved. A focused input in a row that does not move keeps its focus, and in browsers that have moveBefore it keeps focus in moved rows too. Rows of items that left the array stop, and the bindings inside them stop for good; use onCleanup to release what a row set up itself.

A row can be a node or a fragment. Each place where a list is bound keeps its own rows. Inside a computed child, give the list its own element, for example computed(() => (show.get() ? ul(todos.map(render)) : null)); rows are then reused only while that computed does not recalculate.

Index and repeated keys

render receives the item's index at the time its row is created. A reused row keeps that index, even when the item moves. Do not use it to show a position; derive the position from the array if you need it.

A key that appears more than once gets one row per occurrence. Items without a key field all have the key undefined and are matched by position, and the item signal of such a row follows the item at its position. Give each item a stable key when items can move. 

import { ul, li } from 'fiorejs';
import { state, flush } from '@fiorejs/signals';

const items = state([{ key: 'a' }, { key: 'a' }, { key: 'b' }]);

const list = ul(items.for().map((item, index) => li(`${item.get().key}${index}`)));
document.body.append(list);
console.log(list.textContent); // a0a1b2

items.set([{ key: 'b' }, { key: 'a' }, { key: 'a' }]);
flush();
console.log(list.textContent); // b2a0a1: rows moved, labels kept
import { state, flush } from '@fiorejs/signals';

Performance and errors

Lists of a few thousand rows are fine. In Chromium, 1,000 rows with three bound inputs each render in about 40 ms including layout. A change to one row takes well under a millisecond, and adding, removing or swapping rows moves only the rows involved. For much longer lists the number of DOM nodes becomes the limit, so paginate or render only the visible rows.

If render throws, the list keeps the rows it had and stops updating, like any binding that throws. The error is thrown at the end of the flush. See Signals reference for the full list rules.
