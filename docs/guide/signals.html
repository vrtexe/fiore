Signals

A signal is a value that remembers who reads it. When the value changes, the readers run again and nothing else does. This page covers state(), the one signal you write to, and the rules for reading and writing it.

What a signal is

A signal is an object that holds one value. Reading it with get() inside an effect, a computed value or a DOM binding subscribes that reader to the signal. Writing a new value schedules every subscribed reader to run again. A signal that no reader has subscribed to costs nothing and does nothing.

state(value) creates a signal you can write to. Derived signals, made with computed(), are read-only. Both come from @fiorejs/signals; fiorejs itself needs no setup to accept them. 

import { state, effect, flush } from '@fiorejs/signals';

const count = state(0);

effect(() => console.log('count is', count.get())); // logs "count is 0" now

count.set(1);
count.update((n) => n + 1);
flush(); // logs "count is 2", once

The effect ran once for two writes. The runs are batched; Timing and batching explains when they happen.

Reading a signal

get() returns the current value and, when a reader is running, subscribes it. Reading outside any reader, for example in an event handler, only returns the value. Subscription follows what the reader actually reads on its latest run, so a signal read only inside an if branch is a dependency only while that branch runs.

Call the methods on the signal itself. count.set(1) works, but a detached const { set } = count; set(1) does not. Where a function is needed, pass (value) => count.set(value).

Writing a signal

There are three ways to write, and they differ in what they do with the old value:

MethodWhat it does
set(value)Replaces the value.
update(fn)Sets the value that fn(current) returns.
mutate(fn)Lets fn change the current value in place, then always notifies. The return value of fn is ignored.

A write is visible at once: after count.set(5), count.get() returns 5. Only the readers run later.

Equality

set and update compare the new value with the old one using Object.is. An equal value does nothing: no reader runs. Objects and arrays are compared by reference, so a copy always counts as a change. 

import { state, effect, flush } from '@fiorejs/signals';

const name = state('Ada');
const user = state({ name: 'Ada' });

effect(() => console.log('name', name.get()));
effect(() => console.log('user', user.get().name));

name.set('Ada');          // equal: nothing runs
user.set({ name: 'Ada' }); // a new object: the second effect runs
flush();                  // logs "user Ada" again

mutate skips the comparison. It always notifies, even when fn changed nothing, and it notifies also when fn throws, because the value may already have changed.

Arrays and objects

A signal tracks its value, not what is inside it. Pushing to an array you read from a signal changes nothing for the readers. Replace the value instead; copying is cheap because only references are copied. 

import { state, effect, flush } from '@fiorejs/signals';

const todos = state([]);
effect(() => console.log('todos:', todos.get().length));

todos.set([...todos.get(), 'write docs']);     // a new array: readers run
todos.mutate((list) => list.push('publish'));  // same array: readers still run
flush();                                       // logs "todos: 2", once

Use mutate for very large arrays or objects, where copying costs more than it is worth. For deeply nested data, give each field that changes on its own a signal of its own.
