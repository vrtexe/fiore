Timing and batching

A write applies at once, but the effects and bindings that read it run later, together, in one flush on a microtask. This page explains the order inside a flush and how to run it early with flush() or wait for it with tick().

Writes apply at once

After count.set(1), count.get() and every computed that reads count return the new value. Only the readers that are effects or bindings wait for the flush. Several writes in a row cost one run of each reader, and an effect is never re-entered. 

import { state, computed, effect, flush } from '@fiorejs/signals';

const count = state(0);
const double = computed(() => count.get() * 2);
effect(() => console.log('effect sees', count.get())); // logs "effect sees 0"

count.set(1);
count.set(2);
console.log(count.get(), double.get()); // 2 4, at once
flush();                                // logs "effect sees 2", once

A new effect or binding runs at once, so div(count) shows its value before the next line runs.

The flush

The first write that finds a reader waiting queues a flush on a microtask. It runs after the code that wrote has finished, which is why the DOM updates after an event handler, not inside it. Writes made during the flush are handled in the same flush.

  • flush() runs the waiting effects and bindings now. Inside an effect it does nothing, because the running flush handles everything before it ends.
  • tick() returns a promise that resolves after the waiting effects and bindings have run, or right away when none wait. It rejects with the first error of that flush.

Use flush() when the next line needs the DOM, for example to focus or measure an element. In async code, await tick() waits for the flush instead. 

import { div, input } from 'fiorejs';
import { state, flush, tick } from '@fiorejs/signals';

const submitted = state(false);
const field = input.create();
document.body.append(div(submitted.if(() => field)));

console.log(field.isConnected); // false: the branch was not built yet
submitted.set(true);
flush();
console.log(field.isConnected); // true: flush() applied the binding
field.focus();

submitted.set(false);
await tick();
console.log(field.isConnected); // false

Order of the phases

A flush runs three phases, each in creation order:

  1. effect.pre effects;
  2. the other effects and the bindings, so an effect runs before the effects it created;
  3. effect.post effects, which see the DOM after the bindings have updated it.

A write during the flush queues more work, and the flush goes back to the first phase that has some. The first run of an effect.post waits for the next flush. 

import { div } from 'fiorejs';
import { state, effect, flush, tick } from '@fiorejs/signals';

const n = state(0);
const box = div(n);
document.body.append(box);

effect.pre(() => console.log('pre', n.get()));      // logs "pre 0"
effect(() => console.log('effect', n.get()));      // logs "effect 0"
effect.post(() => console.log('post', n.get(), 'DOM shows', box.textContent));

await tick(); // logs "post 0 DOM shows 0": the post effect's first run
n.set(1);
flush();      // logs "pre 1", "effect 1", "post 1 DOM shows 1"

Tests

Tests call flush() after their writes and before their assertions, so they do not depend on microtasks. An error of an effect or binding is thrown by flush(), so a test fails on it instead of seeing an uncaught error later. 

import assert from 'node:assert/strict';
import { span } from 'fiorejs';
import { state, flush } from '@fiorejs/signals';

const count = state(0);
const view = span(count);

count.update((n) => n + 1);
assert.equal(view.textContent, '0'); // the binding has not run yet
flush();
assert.equal(view.textContent, '1');

An effect or binding that throws is stopped, the other effects of the flush still run, and the first error is thrown at the end. See Effects for errors and the 100-runs loop limit, and the reference for the exact rules.
