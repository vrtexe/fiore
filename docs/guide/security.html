Quick start

Security

fiore creates DOM nodes and sets text as text, so ordinary use is safe against script injection. The risks come from a few features that take data seriously on purpose. This page lists them and how to avoid each one.

The plain-object data rule

This rule belongs to the builder API, and JSX has no data object: whatever sits between the tags is children, and a string is shown as text. JSX has its own risks, which are spreading an object whose keys you do not control and putting an untrusted URL in an attribute. A spread copies every key of the object onto the element, so a key such as innerHTML sets that property:

A tag called with a plain object reads that object as the data object, with the keys props, attrs, on and children. Anything else is the children. If the object comes from untrusted data such as parsed JSON, storage or a message, an attacker can choose its keys: { "props": { "innerHTML": "…" } } sets the HTML of the element. 

import { li, p, ul } from 'fiorejs';

// A message from a server, a form, storage or postMessage: nobody checked what it holds
const message = JSON.parse('{"props":{"innerHTML":"<img src=x onerror=alert(1)>"}}');

const unsafe = p(message); // read as the data object: sets innerHTML
const safe = p.create(message); // read as children: never sets props
const rows = ul(['plain text', '<b>stays text</b>'].map((text) => li.create(text)));

document.body.append(unsafe, safe, rows);
const message = JSON.parse('{"innerHTML":"<img src=x onerror=alert(1)>"}');
const text = '<b>stays text</b>';

const safe = <p>{text}</p>; // a child: a string is shown as text
const unsafe = <p {...message} />; // a spread: sets innerHTML

document.body.append(safe, unsafe);

Show untrusted values as children, <p>{value}</p>, and never spread an object that came from untrusted data into a tag. Spread only objects you wrote, or build the object from a fixed list of keys. See JSX.

Pass untrusted values to .create(value) or to { children: value }, which always treat the value as children, and a string is shown as text. The rule is simple: literal text from your own code can use p('Hello'), and a value you did not write goes through create. See Elements and tags.

on* attributes are ignored

In JSX every prop whose name starts with on, in any case, is a listener and never an attribute. A string such as onclick="alert(1)" is not set as an attribute, so no script runs from it. The name after on is used as the event name, so a hyphenated name such as on-tap listens to the event -tap and does not set an attribute either. Pass a function.

An attribute whose name is on followed by letters only, such as onclick or onload, in any case, is never set, because the browser would run its text as script. This applies to attrs and to bound attributes alike. A hyphenated name such as on-tap is set, since it is not a handler. Attach listeners with on, which takes functions. 

import { div } from 'fiorejs';

const element = div.attrs({ onclick: 'alert(1)', ONLOAD: 'alert(2)', 'on-tap': 'open', title: 'Hello' }).create('Text');

document.body.append(element);
console.log(element.getAttributeNames()); // [ 'on-tap', 'title' ]
const element = <div onclick="alert(1)" ONLOAD="alert(2)" title="Hello">Text</div>;

document.body.append(element);
console.log(element.getAttributeNames()); // [ 'title' ]

innerHTML is your responsibility

innerHTML is a property like any other, so <div innerHTML={html} /> sets it, and fiore does not sanitize the string. Children are text nodes and are safe, so prefer them. Use innerHTML only for markup you wrote, or for HTML that a sanitizer has cleaned first.

innerHTML is a property like any other, so props({ innerHTML }) sets it, and fiore does not sanitize the string. Children are text nodes and are safe, so prefer them. Use innerHTML only for markup you wrote, or for HTML that a sanitizer has cleaned first. 

import { div } from 'fiorejs';

const comment = '<img src=x onerror=alert(1)> hello';

const text = div.create(comment); // a text node: shown as typed
const trustedHtml = div.props({ innerHTML: '<strong>Static markup you wrote</strong>' }).create();
const risky = div.props({ innerHTML: comment }).create(); // runs the handler in a browser

document.body.append(text, trustedHtml, risky);
const comment = '<img src=x onerror=alert(1)> hello';

const text = <div>{comment}</div>; // a text node: shown as typed
const trustedHtml = <div innerHTML="<strong>Static markup you wrote</strong>" />;
const risky = <div innerHTML={comment} />; // runs the handler in a browser

document.body.append(text, trustedHtml, risky);

The same goes for srcdoc and for URLs, as in <iframe srcdoc={html} /> and <a href={url}>. Attribute values are passed to setAttribute unchecked, so a javascript: URL in href or src runs when it is followed. Check the scheme of a URL that comes from untrusted data.

Prototype-pollution keys

When fiore copies props into an element it assigns own keys only and skips __proto__, constructor and prototype. A JSON payload with such keys cannot reach Object.prototype through the library, and a polluted prototype adds nothing to an element. 

import { div } from 'fiorejs';

const payload = JSON.parse('{"__proto__":{"polluted":true},"constructor":{"prototype":{"polluted":true}},"title":"ok"}');

const element = div.props(payload).create('Hi');

document.body.append(element);
console.log(element.title, ({}).polluted); // ok undefined
const payload = JSON.parse('{"__proto__":{"polluted":true},"constructor":{"prototype":{"polluted":true}},"title":"ok"}');

const element = <div {...payload}>Hi</div>;

document.body.append(element);
console.log(element.title, ({}).polluted); // ok undefined

A JSX spread goes through the same code, so __proto__ cannot reach Object.prototype there either. The other keys are still applied: the example sets a constructor attribute with the text [object Object], and a payload that sets innerHTML still sets it. Treat this as a safety net, not as permission to spread untrusted objects.

This protects the prototype, not the other keys: a payload that sets innerHTML still sets it. Treat this as a safety net, not as permission to pass untrusted objects to props.

Attribute names never from untrusted data

The name of an attribute decides what it does: srcdoc, href and style all have effects. Do not build attrs or props from the keys of untrusted objects, in the core API or by spreading them in JSX (a key such as innerHTML or srcdoc sets that property or attribute). If the user may pick attributes at all, filter their names against a list you control, and check the values you allow. 

import { a } from 'fiorejs';

const allowed = new Set(['title', 'rel', 'aria-label']);
const fromUser = JSON.parse('{"title":"Docs","onmouseover":"alert(1)","href":"javascript:alert(1)"}');

const attrs = Object.fromEntries(Object.entries(fromUser).filter(([name]) => allowed.has(name)));
const safeUrl = (value) => (['https:', 'http:'].includes(new URL(value, 'https://example.com').protocol) ? value : null);

document.body.append(a.attrs({ ...attrs, href: safeUrl('javascript:alert(1)') ?? '#' }).create('Docs'));
